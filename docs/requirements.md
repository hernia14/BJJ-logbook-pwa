# BJJ Drill App — Phase 0 要件整理

> このドキュメントは実装方針を決めるための論点整理である。**柔術の技術内容・IBJJFルールの具体値は一切含まない。** それらはPhase 2（一次情報＝あなたの`ingest/raw/`とルール原本から確定）で扱う。

---

## A. 技術知識の原子化（最重要論点）

### A-1. 分解軸と推奨

技1つを丸ごと1枚のカードにすると「答えが長すぎて反復学習に機能しない」というあなたの懸念はその通りで、これは学習科学でいう**単一想起原則（1カード1事実）**に反する設計になる。1枚のカードで複数の事実を問うと、部分的に思い出せた場合の自己評価が曖昧になり、SRS（間隔反復）のスケジューリング精度が崩れる。

推奨する分解軸（技オブジェクトの固定スロット）：

| スロット | 内容 | カード化の単位 |
|---|---|---|
| 前提ポジション/状況 | この技が成立する体勢 | 1事実=1カード |
| グリップ/コントロール | どこを何の目的で握る/制するか | グリップ1箇所=1カード（複数あれば複数枚） |
| 角度・体重配分 | 体の向き、荷重先 | 1カード |
| 手順（プロシージャ） | 実行ステップ | §A-2参照（順序型） |
| 仕上げ（フィニッシュの決め手） | 効かせるための最終条件 | 1カード |
| よくある失敗 | 典型的なミス | ミス1種=1カード |
| 失敗の帰結（因果） | そのミスが起きると何が起きるか | §A-4参照（因果ペア） |
| 禁忌 | やってはいけないこと・危険性 | `content/safety/`へ分離（§F参照） |
| カウンター | 相手の対抗手段 | 1カード（技同士のリンクとして双方向タグ） |
| 次への連携 | 派生・コンボ | 1カード |
| なぜ効くか（原理） | 力学・原理の理解 | §A-3参照（原理型） |

**推奨**：技ごとに「技メタデータ（frontmatter）＋スロット別の原子カード群」という構造をとり、1スロット=1カードではなく**1スロット内の独立した事実の数だけカードを作る**。スロットはカード生成のガイドであって、カード数の単位そのものではない。

**トレードオフ**：スロットを厳密なテンプレートにすると、テンプレートに収まらない技（原理寄りの技、複合技）で無理な当てはめが起きる。→ スロットは「推奨カテゴリ」として運用し、必須ではなく空欄可とする。

### A-2. 手順（プロシージャ）とordering型

10工程ある手順をそのまま1つのordering型カードにするのは認知負荷理論（作業記憶は概ね4±1〜7±2チャンク）に反し、正答率が構造的に低くなる＝正しく覚えているのに「不正解」と判定される事故が起きる。

**推奨**：
- 10工程を「準備（セットアップ）」「実行（エントリー〜制圧）」「フィニッシュ」のような**3フェーズ程度に分割**し、各フェーズ内は最大5項目程度のordering型カードにする。
- 加えて、ordering型だけに頼らず「工程Xの直後に来るのは？」という**単発の順接カード**を補助的に用意する（ordering型が苦手とする「ある1点の順序関係」をピンポイントで問える）。

**トレードオフ**：フェーズ分割の境界の引き方が主観的になりうる → 境界の決定はordering型カード生成時に人間（あなた）がレビューする運用にする（§H参照）。

### A-3.「なぜ効くのか」カードの設計

暗記と原理理解は別の記憶回路であり、丸暗記カードだけでは「体系が繋がっていない孤立した知識」になりやすい。

**推奨**：原理型カードを独立したカードタイプ（`type: principle`）として扱い、以下のような双方向の問い方を用意する。
- 原理→効果型：「この原理（フレーム/ベース/角度/圧など）が働くと何が起きるか」
- 効果→原理型：「この現象が起きているとき、働いている原理は何か」
- 技→原理型：「この技でこの原理はどこに現れているか」（`content/techniques/concepts/`の概念カードと技カードを相互リンクするタグ設計にする）

これにより、単なる記憶ではなく「概念カードの理解が複数の技カードの正答率に影響する」構造ができ、概念の汎用性を測定できる。

**トレードオフ**：原理カードは自由記述になりやすく自動採点が難しい → §Gの自己採点方式と組み合わせる。

### A-4.「よくある失敗→結果」の因果型カード

**推奨**：1つの因果関係を**双方向2枚のペア**として生成する。
- 原因→結果：「このミスをするとどうなるか」
- 結果→原因：「この状況（症状）が起きた原因として最も可能性が高いミスは」

2枚には共通の`causal_pair_id`を持たせ、誤り報告（§H）があった場合に片方だけでなくペア全体を隔離できるようにする。

### A-5. カード間の依存関係の扱い

**推奨**：依存関係（前提カードを知らないと解けない）は**出題スケジューリングをブロックする硬い制約にはしない**。SRSアルゴリズムの間隔計算はカードごとに独立しているのが基本設計であり、依存関係を出題順に強制反映させるとスケジューリングの精度そのものを壊す。

代わりに依存関係グラフ（DAG）はメタデータとして持たせ、以下の2用途に限定する：
1. **初回導入順序**：新しいデッキ/技を初めて学習する際の推奨学習順の算出
2. **診断表示**：あるカードで連続して失敗した場合に「前提となるこのカードを先に復習しては」と提案する補助機能

**トレードオフ**：依存関係を完全に無視すると「土台を知らないまま応用カードだけ正解し続ける」偽の定着が起きうる → 診断表示で緩く補正する程度に留めるのが費用対効果として妥当。

### A-6. 1技あたりのカード数の目安

**推奨**：詳細な技で**8〜15枚程度**を目安上限とする（禁忌・安全カードは別カウント、§F）。

**過剰分解の害**：
- 同一技の細部カードが連続出題されやすくなり、パターン記憶（実質的な連想ゲーム）で解けてしまい、真の想起にならない
- SRSの間隔がカードごとに独立でも、母数が増えると同技カード同士が近接して出題される確率が上がる

**対策**：SRSの自然な分散に加えて、**1セッション内で同一技IDから出題できる上限枚数（例：3枚）**をアプリ側の出題ロジックに持たせる。

## B. 出題形式の選定

| 形式 | 適する分解軸 | 注意点 |
|---|---|---|
| 4択 | ポジション/用語識別、ルール系の客観的事実 | 「コツ」系には不向き（下記参照） |
| 自由入力（自己採点） | 手順の要点、原理説明、コツ | 採点は自動化せず自己申告制を基本とする（§G） |
| 自由入力（自動採点） | 用語名、数値、固有名詞など短答のみ | 表記ゆれ処理が必須（§G） |
| 正誤（○×） | 禁忌の是非、よくある誤解の訂正 | 単純だがあて推量率50%、補助形式として使う |
| 順序並べ替え | 手順（3〜5工程のチャンク） | §A-2参照、10工程を丸ごとは不可 |
| 図/画像からのポジション判別 | ポジション識別、グリップ形状 | `content/assets/`の図版整備が前提。Phase 0では設計のみ |
| 穴埋め | 定義文の核心語、原理の名称 | 用語カードと相性が良い |

**「コツ」を4択にする危険性**：コツ（感覚的な勘所）を4択にすると、選択肢の表現の巧拙から**消去法で正解が逆算できてしまう**。たとえば誤答選択肢が明らかに不自然な言い回しだと、コツの記憶がなくても正解できる。これは「テストで点が取れる」が「実際にマットの上で使える記憶になっていない」状態を生み、あなたが最も避けたい「誤学習の定着」の一種（正確には"見せかけの定着"）にあたる。

**推奨**：コツ系は自由入力・自己採点を基本形式とし、4択はどうしても選択肢が作れる場合の補助形式に留める。

## C. 間隔反復アルゴリズム

| | Leitner | SM-2 | FSRS |
|---|---|---|---|
| 実装コスト | 低（箱移動のみ） | 中（カードごとease factor） | 高（統計モデル、パラメータ最適化器） |
| パラメータ調整 | 不要 | 不要（アルゴリズム内蔵） | 必要（十分な復習履歴でのフィッティングが前提） |
| コールドスタート | 問題なし | 問題なし | 履歴が少ないと精度が出ない |
| 「1日10分」運用適合 | やや粗い | 良好 | 理論上最適だが恩恵が出るのはデータ蓄積後 |

**推奨**：初期実装は**SM-2**を採用する。理由は、実装コストと精度のバランスが良く、コールドスタート問題がなく、個人〜道場配布規模の運用量ではFSRSの統計的優位性が生きるほどのデータ量が集まらない可能性が高いため。FSRSは「Phase後期の拡張候補」として明記し、無理に初期採用しない。

**自己評価の粒度**：「頭で分かる」と「体で分かる」の乖離は本質的な問題である。ここで欲張って2軸評価（想起品質×実践自信度）をSRSの計算に両方組み込むと、アルゴリズムが複雑化し閾値調整が必要になり、「調整不要」というSM-2選定の利点を失う。

**推奨**：SRSの間隔計算には**想起品質のみ**（通常のSM-2の0〜5評価）を使う。「体でまだ確認していない」は**間隔計算に影響しない補助タグ**（例：`未検証`フラグ）として別途記録し、道場での実技確認時にそのタグが付いたカード一覧を出せるようにする程度に留める。

## D. 知識タクソノミー（多重タグ設計）

技は複数ポジションに跨るため、**単一階層フォルダ分類＋多面的タグ**のハイブリッドにする。

- **主分類**（1つ、必須）：`content/`配下のディレクトリ位置と一致させる（ポジション/パスガード/スイープ/絞め/関節技/エスケープ/テイクダウン/トランジション/概念/安全/ルール/用語/歴史）
- **ポジションタグ**（複数可）：この技が有効な体勢すべてを列挙
- **概念タグ**（複数可）：フレーム/ベース/角度/圧/ハンドルなど、原理カードとのリンクに使う
- **カード種別タグ**：事実/手順/原理/因果/安全
- **ソース状態タグ**：draft/reviewed（§H）
- **ルールバージョンタグ**：IBJJF v6.0固定（§E）

frontmatter（YAML）にこれらを配列として持たせ、`content/`のMarkdownファイル自体を単一の真実源（Single Source of Truth）とし、クイズ用データベース（JSON/SQLite等）はビルドスクリプトによる生成物として扱う。

## E. IBJJF v6.0の扱いと将来のv7.0対応

ルールカードは必ず「Rule Book v6.0」または「Rules Update Guide v6.0」のどちらか＋該当セクション番号を`source`フィールドに記録する。

**v7.0が出た際に影響カードを機械的特定するための設計**：
- 条文単位で安定した`clause_id`を振り、`clause_id → {version, section番号, カード本文のハッシュ}`の対応台帳（`content/rules/`内のレジャーファイル）を保持する
- 新バージョンが出たら、人間が新旧の該当セクションを突き合わせ、本文ハッシュが変わった/セクション番号が変わった条文に紐づくカードだけを機械的に一覧化し、レビュー対象としてフラグを立てる
- PDFの自動差分解析のような魔法は狙わない（誤検知/見逃しのリスクが高く、ルール系は誤りが致命的なため人間レビューを介在させる設計にする）

## F. 安全・禁忌カードの特別扱い

**他カテゴリと同列に扱えない理由**：技術知識の誤りは「次に覚え直せば済む」が、禁忌知識の誤りは**身体的な怪我に直結**する。誤りのコストが非対称であり、通常カードと同じ生成・レビューフローに乗せるのは危険。

**推奨する分離の仕組み**：
1. **生成元の制限**：`content/safety/`配下のカードは、Claudeが新規の安全主張を創作することを禁止する。Claudeが行えるのは、あなたの`ingest/raw/`に書かれた内容の**言い回し整形・カード化のみ**（CLAUDE.mdに明文のルールとして明記）
2. **人間署名の必須化**：frontmatterに`reviewed_by`と`reviewed_date`を必須フィールドとし、これが空のファイルはビルド時にエラーで弾く（CI/lintでの機械的強制）
3. **出題時の視覚的警告**：安全カードには専用のアイコン/色分けを施し、「これは安全上重要な知識である」と利用者に常に意識させる（色だけに依存しないアクセシビリティ配慮、§I参照）
4. **復習頻度の下限保証**：SM-2の通常計算に加え、安全カードには**最大間隔の上限（キャップ）**を設け、アルゴリズム上どれだけ習熟しても一定期間ごとに強制再出題する（重要度に応じたポリシーオーバーライド）

## G. 日本語の表記ゆれと解答判定

**正規化すべき軸**：全角/半角、カタカナ/ひらがな、長音記号の表記ゆれ、中黒の有無、前後の空白、大文字小文字（ローマ字表記がある場合）。

**エイリアス辞書**：柔術用語は流派・道場・世代によって表記が割れる（例：同じ技でもカタカナ表記が複数存在する、英語由来の訳語が複数ある、等）。カードごとに「正答＋許容エイリアス配列」を明示的に持たせる。**グローバルな類義語辞書による自動吸収はしない**——用語の意味範囲がずれるカテゴリ違いの誤答を誤って正解にしてしまう危険があるため。

**編集距離閾値**：短い単語（用語名・固有名詞）の**タイプミス救済のみ**に限定して小さい閾値を適用する。文章レベルの解答には適用しない。

**部分一致の危険性**：部分一致/包含判定を安易に使うと、上位概念の名称が下位概念の解答としても一致してしまう、あるいは全く別の答えが文字列として偶然含まれてしまう、といった誤判定が起きうる。**推奨**：自動採点は「用語名・数値など短答カードのみ」に限定し、それ以外（手順の要点・原理説明・コツ）はすべて**自己採点方式**（模範解答を見て自分で○×を申告）にする。自動判定の対象を狭く保つことが、誤学習防止の観点で最も費用対効果が高い。

## H. 誤学習防止ワークフロー

あなたの「唯一許容できない失敗」に対応する、最重要の運用設計。

1. **誤り報告フロー**：クイズ実行中、任意のカードに「誤り疑いあり」フラグを立てられるUIを用意する。報告されたカードは即座に出題プールから除外（隔離）され、解決するまで二度と出題されない
2. **出所必須化**：すべてのカードのfrontmatterに`source`（`ingest/raw/`の該当ファイル、またはルール文書のセクション番号）を必須とし、欠落しているカードはビルド時にエラーとする
3. **未レビューカードの隔離**：Claudeが`ingest/raw/`の生メモからカード化した直後は`status: draft`とし、本番のクイズプールから自動的に除外する。`status: reviewed`への変更はあなた自身の手動レビューでのみ行う
4. **資料改訂への追従**：`ingest/raw/`の元メモやルール文書が更新された場合、引用元のコンテンツハッシュをカードのfrontmatterに保持し、上流が変化したらハッシュ不一致で自動的に`stale`フラグを立て、再レビューされるまで出題を止める

この4点はいずれも「機械的に強制できる」設計にすることが肝で、運用ルールとして"覚えておく"だけの仕組みは長期的に必ず形骸化する。

## I. 非機能要件

- **オフライン動作**：PWA + Service Workerによる事前キャッシュ。初回ロード後は完全にネットワーク不要
- **起動速度**：Markdownのランタイムパースは避け、ビルド時に静的なJSON（または後述のDBファイル）へ変換したものをバンドルする
- **5000カード規模の性能**：この規模ならSM-2のスケジューリング計算自体はO(n)で軽量。ストレージは5MB上限のあるlocalStorageではなく、IndexedDB（またはsql.js/wasmによるSQLite）を推奨
- **履歴のエクスポート/インポート**：復習履歴・習熟度をJSONでエクスポート/インポートできるようにし、端末紛失時の消失や複数端末（スマホ＋タブレット等）間の手動同期に対応する。サーバー同期は行わない
- **アクセシビリティ**：文字サイズ変更対応、十分なコントラスト比（特に安全カードの警告色は色覚多様性に配慮し色だけに依存せずアイコン/テキストも併用）、モバイルでのタップ領域サイズ確保
- **道場配布時の責任範囲**：これは工学的な設計事項ではなく、指導者としてのあなたが判断すべき事項（免責文言、生徒への説明範囲等）。本ドキュメントでは決定せず、質問として下に挙げる
- **サーバーレス前提の攻撃面**：個人情報を持たずサーバーも持たないため主要リスクは、(1) ビルド時の依存パッケージによるサプライチェーンリスク（lockfile固定、依存最小化で対応）、(2) カード内容をHTMLとして描画する場合のXSS（生Markdownをサニタイズして描画し、`content/`由来のテキストに生HTML実行を許さない）、(3) 道場配布時にホスティングする場合のService Worker/キャッシュ改ざん（HTTPS必須）。個人情報を一切扱わない設計自体が最大の防御になっている
